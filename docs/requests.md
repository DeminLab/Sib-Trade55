# Приём заявок

[README](../README.md) · [Архитектура](architecture/backend-api.md) · [Окружение и запуск](DEPLOYMENT.md)

Сценарий каталога обновлён 14 октября 2026 года.

Цены товаров на витрине не публикуются: стоимость согласуется индивидуально. Клиент добавляет товары и варианты в подборку, меняет количество и отправляет единую заявку на `/quote`. Подборка сохраняется в браузере. Имя и телефон обязательны; email необязателен для звонка и обязателен при выборе ответа по почте. Заявка не создаёт оплаченный заказ. Сервер обнуляет старые клиентские цены и отмечает позиции как требующие расчёта.

Старые `/cart` и `/checkout` перенаправляют на `/quote`; сохранённые товары корзины переносятся в подборку. Телефон и график для самостоятельного звонка берутся из настроек сайта, с пояснением «время Омска (UTC+6)». Заявки принимаются круглосуточно, ответ — в рабочие часы.

Обращения (`/contact`), запросы КП (`/quote`) и заявки с чертежами (`/custom`) сохраняются в текущей SQLite базе (`SQLITE_DATABASE_PATH`). Таблицы `customer_requests` и `request_attachments` создаются автоматически. Файлы хранятся в базе вместе с заявкой, а не в публичной директории.

Администратор видит обращения в `/admin/contacts`, КП в `/admin/quotes`, задачи по ТЗ в `/admin/custom-requests`. Можно открыть детали, скачать файлы, изменить статус и повторить неудачную отправку уведомления. API списка, изменения статуса и скачивания проверяет подписанную сессию администратора. Кэширование ответов с данными заявок отключено.

Файлы: до 5 вложений по 10 МБ; PDF, JPG, PNG, DWG, DXF. Файлы выдаются только как скачиваемые вложения. Nginx разрешает до 52 МБ на `/api/custom-requests`, остальные маршруты ограничены 20 МБ. JSON заявки ограничены 512 КБ, тело проверяется до разбора формы.

## API и статусы

| Форма | Публичный API | Тип в базе | Админка |
| --- | --- | --- | --- |
| Обращение | `POST /api/contact` | `contact` | `/admin/contacts` |
| Запрос КП | `POST /api/quotes` | `quote` | `/admin/quotes` |
| ТЗ с файлами | `POST /api/custom-requests` | `custom` | `/admin/custom-requests` |

Успешный ответ содержит `success`, `requestId`, `requestNumber` и `message`. Статусы заявки: `submitted`, `processing`, `completed`, `cancelled`. Состояния уведомления: `not_configured`, `pending`, `sent`, `failed`.

Список загружается через `GET /api/admin/requests?kind=contact` (также `quote` и `custom`, параметры `page`, `limit`). Для смены статуса отправляется `PATCH /api/admin/requests/[id]` с `{ "status": "processing" }`, для повтора — с `{ "action": "retry_notification" }`. Файл скачивается через `GET /api/admin/requests/[id]/files/[fileId]`.

Заказы из корзины — отдельный процесс: `POST /api/orders` сохраняет заявку в таблице `orders`, а `/admin/orders` показывает список. Этот маршрут не отправляет уведомления Telegram.

## Telegram

В `.env` задайте `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`, затем перезапустите приложение. Эти переменные передаются через `environment` обеих Compose-конфигураций. Для прямого standalone-запуска загрузите окружение по [инструкции](DEPLOYMENT.md). Токен нельзя добавлять в Git. Получатель должен заранее начать диалог с ботом, либо бот должен иметь возможность писать в указанный групповой чат.

Уведомление содержит номер, тип заявки, контактные данные и краткое описание задачи. Сами файлы остаются в защищённой админке. Заявка сохраняется до обращения к Telegram. Ошибка Telegram не отменяет сохранение и не приводит к ошибке отправки формы; админка показывает состояние уведомления. Повторная отправка выполняется кнопкой, автоматически фоновые повторы не запускаются. При отсутствии настроек приём заявок работает, состояние уведомлений — «Telegram не подключён».

## Проверка

После изменения схемы перезапустите локальный Next.js процесс.

```powershell
node --test tests/requests-store.test.mjs
npm run build
node tests/requests.integration.mjs
$env:RUN_BROWSER = '1'
node tests/requests.integration.mjs
```

Тесты используют отдельную временную SQLite базу и тестовую сессию. Telegram запросы в тестах хранилища подменены, в тестах сервера Telegram отключён. Интеграционный тест запускает собранный standalone сервер, проверяет валидацию, доступ по ролям, принадлежность вложений, статусы и сохранность после перезапуска. Браузерная проверка требует установленный Microsoft Edge, использует Playwright и проверяет три формы и админку на ширинах 320, 768, 1024 и 1440 px. После браузерной проверки удалите временную переменную: `Remove-Item Env:RUN_BROWSER`.

Сборка может обращаться к базе проекта; отдельная временная база интеграционного теста не изолирует предшествующий `npm run build`. Для изолированной сборки заранее задайте отдельный `SQLITE_DATABASE_PATH`.

Это локальная проверка. Для проверки доставки Telegram нужны реальные настройки; для проверки production маршрутизации нужно отдельно запустить Docker/Nginx.
