# Изображения каталога

Изображения `/api/catalog/media/…` в интерфейсе используют заранее подготовленные WebP нужной ширины. Оригинальные URL и байты в SQLite сохранены. Размеры ограничены списком в `src/lib/image-sizes.ts`; произвольные размеры возвращают 400.

Копии сохраняются в `<каталог данных>/image-cache-v1` и переживают пересоздание контейнера через `sib_trade_data`. Новые загрузки готовят ширины 64, 128, 256, 384, 768 и 1200 до ответа админке. Другие размеры создаются при первом запросе. Обработка последовательная, одинаковые одновременные запросы объединяются; готовые копии читаются без обращения к SQLite.

Кеш обычного оптимизатора Next (баннеры и другие статические изображения) сохраняется отдельным томом `sib_trade_image_cache`.

## Предварительная обработка существующих фотографий

Локально после инициализации базы:

```powershell
node scripts/prepare-image-cache.mjs
```

На сервере после обновления и пересоздания контейнера:

```sh
docker compose exec app node scripts/prepare-image-cache.mjs
```

По умолчанию готовятся первые фотографии активных товаров и изображения категорий. `--all` обрабатывает все изображения базы, включая архивные и дополнительные кадры; это требует больше времени и диска. Повторный запуск пропускает существующие копии. Скрипт открывает SQLite только для чтения, создаёт только файлы кеша и завершает работу с кодом 1 при ошибках.

При изменении настроек кодирования нужно повысить версию каталога кеша и параметра `v` в загрузчике. При замене фотографии используйте новый URL: кеш браузера для этих ресурсов рассчитан на год.

## Проверка после развёртывания

Сравнить холодную и повторную загрузку `/shop` на мобильном и настольном экранах: размер выбранного изображения, время ответа, завершение загрузки видимых карточек. После пересоздания контейнера убедиться, что файлы обоих кешей сохранились. Локальный dev-сервер не доказывает скорость production на VPS.
